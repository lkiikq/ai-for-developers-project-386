# Календарь звонков

[![hexlet-check](https://github.com/lkiikq/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/lkiikq/ai-for-developers-project-386/actions)

Сервис для бронирования времени звонков — упрощённый аналог [Cal.com](https://cal.com), разработанный совместно с ИИ.

Владелец календаря один и задан заранее. Он заводит типы встреч и смотрит список предстоящих событий. Гость без регистрации выбирает тип встречи, открывает календарь на ближайшие 14 дней и записывается на свободный слот.

В проекте **нет авторизации, личных кабинетов и интеграций с внешними календарями** — функциональность намеренно ограничена.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Стек

- **Бэкенд:** Node.js + Express — REST API
- **Фронтенд:** React + Vite (SPA)
- **Контракт API:** TypeSpec → OpenAPI (YAML) → сгенерированный клиентский SDK для фронтенда (`@hey-api/openapi-ts`, fetch)
- **Хранение данных:** in-memory (обычные JS-объекты в памяти процесса), **без базы данных**
- **Тесты бэкенда:** Jest + Supertest
- **Линтер:** ESLint
- **Окружение разработки:** mise (`mise.toml` — версии инструментов, задачи, daemons), git-хуки — hk (`hk.pkl`)
- **Развёртывание:** Docker (один образ: бэкенд + собранный фронтенд)

## ⚠️ Хранение данных — важно

Все данные (типы встреч, бронирования) хранятся **только в оперативной памяти** сервера. **При перезапуске бэкенда все записи сбрасываются.** Это осознанное упрощение учебного проекта:

- не подключать БД (SQLite, Postgres, MongoDB и т.д.), файловое сохранение или ORM без явного запроса пользователя;
- хранилище реализуется в одном модуле (`server/src/store.js`), чтобы при необходимости его можно было заменить на БД, не меняя остальной код;
- тесты должны сбрасывать состояние хранилища перед каждым тестом.

## Доменные правила (зафиксированные параметры)

Эти параметры выбраны и **зафиксированы в спецификации** — менять их только по явному запросу пользователя:

- **Владелец календаря:** один, предопределён. Авторизации нет, действия владельца не защищены (учебное упрощение).
- **Часовой пояс:** `Asia/Almaty` (UTC+5). Все даты и время в API — в этом часовом поясе.
- **Рабочие часы владельца:** пн–пт, 10:00–18:00. Выходные (сб, вс) недоступны для записи.
- **Окно бронирования:** 14 календарных дней, **начиная с завтрашнего** (включительно: `завтра … завтра+13`). Окно скользящее — сдвигается с течением времени. Даты вне окна отклоняются (`400`). Записаться «на сегодня» нельзя — все слоты по определению в будущем.
- **Длительность слота:** равна длительности выбранного типа встречи.
- **Шаг доступных стартов:** 30 минут (10:00, 10:30, 11:00, …) независимо от длительности встречи. Последний старт — такой, чтобы встреча закончилась не позже 18:00.
- **Запрет пересечений:** интервалы полуоткрытые `[start, end)`. Одно и то же время нельзя занять дважды, **даже разными типами встреч**; любое частичное наложение запрещено. Встреча может начинаться ровно в момент окончания предыдущей (back-to-back разрешён).
- **Конкурентность:** правила действуют и для одновременных запросов. Проверка пересечения и создание брони выполняются **атомарно** — одной синхронной операцией, без `await` между проверкой и записью (Node.js однопоточен, поэтому check-and-set нельзя разрывать асинхронными вызовами).

## Контракт API: TypeSpec → OpenAPI → SDK

Единственный источник правды об API — **TypeSpec-контракт** в `contract/main.tsp`.

```
contract/main.tsp ──compile──> contract/openapi.yaml ──generate──> client/src/api/generated/
```

Порядок работы при любом изменении API:

1. Правим TypeSpec-контракт (`contract/main.tsp`).
2. Компилируем в OpenAPI: `cd contract && npm run compile` → обновляется `contract/openapi.yaml` (файл коммитим в репозиторий).
3. Реализуем/обновляем эндпоинты на бэкенде — **сервер обязан соответствовать `openapi.yaml`**.
4. Генерируем клиентский SDK: `cd client && npm run generate:api` → обновляется `client/src/api/generated/`.

Правила:

- `contract/openapi.yaml` и `client/src/api/generated/` — **сгенерированные файлы, руками не редактируются**;
- фронтенд обращается к API **только через сгенерированный SDK** — никаких ручных `fetch('/api/...')` в компонентах;
- несовпадение бэкенда со спецификацией считается багом.

```
│   └── package.json
├── server/                  # Express-бэкенд, реализует openapi.yaml
│   ├── src/
│   │   ├── index.js         # точка входа, запуск сервера
│   │   ├── app.js           # сборка Express-приложения (для тестов)
│   │   ├── store.js         # in-memory хранилище данных
│   │   └── routes/          # роуты API (по одному файлу на ресурс)
│   ├── tests/               # тесты (Jest + Supertest)
│   └── package.json
├── client/                  # React-фронтенд (Vite)
│   ├── src/
│   │   ├── api/generated/   # сгенерированный SDK, не редактировать
│   │   ├── pages/           # страницы (по одному компоненту на страницу)
│   │   └── components/      # переиспользуемые компоненты
│   └── package.json
├── mise.toml                # версии инструментов, задачи, хуки и daemons mise
├── hk.pkl                   # git-хуки (hk): pre-commit — проверки, commit-msg — формат коммита
├── .github/workflows/check.yml  # CI: `mise run check` на каждый push
├── Dockerfile               # multi-stage: сборка клиента + сервер
└── README.md
```

Правила:

- вся бизнес-логика (расчёт слотов, проверка пересечений, окно 14 дней) живёт **только на бэкенде**; фронтенд — тонкий клиент;
- в dev-режиме фронтенд (`localhost:5173`) проксирует `/api/*` на бэкенд (`localhost:3000`) через Vite;
- в проде (Docker) бэкенд сам раздаёт собранный фронтенд (`client/dist`) и API на одном порту `3000`.

```bash
git clone https://github.com/lkiikq/ai-for-developers-project-386.git
cd ai-for-developers-project-386

# Вариант с mise (рекомендуется): ставит зафиксированные версии инструментов
# (node, hk, pitchfork), а хук postinstall — зависимости всех пакетов
mise install
hk install --mise   # git-хуки: pre-commit — проверки, commit-msg — формат коммита

# Либо вручную, без mise:
cd contract && npm install   # TypeSpec-контракт

```

Переменные окружения не требуются. Порт бэкенда — `3000`, фронтенда в dev-режиме — `5173`.

## Запуск

### Docker (основной способ)

Приложение собирается в один Docker-образ и запускается в контейнере:

```bash
docker build -t call-calendar .
docker run --rm -p 3000:3000 call-calendar
# открыть http://localhost:3000
```

Образ multi-stage: первый этап собирает фронтенд (`vite build`), второй — поднимает Express, который раздаёт API и статику фронтенда на порту `3000`.

### Локально (для разработки)

```bash
# Оба сервера фоном, как daemons mise (статус: mise daemons ls, стоп: mise daemons stop)
mise daemons start

# Либо по-старинке, в двух терминалах:
# Терминал 1 — бэкенд (http://localhost:3000)
cd server && npm run dev

# Терминал 2 — фронтенд (http://127.0.0.1:5173)
cd client && npm run dev
```

Проверка работоспособности бэкенда: `GET http://localhost:3000/api/health` → `{ "status": "ok" }`.

## Сценарии использования

Два типа пользователей (без регистрации и авторизации): **владелец** настраивает и наблюдает, **гость** бронирует.

1. **Создание типа встречи (владелец).** Владелец заводит тип встречи: название, описание, длительность в минутах. Например, «Созвон на 30 минут».
2. **Предстоящие события (владелец).** Владелец видит список всех предстоящих бронирований всех типов, отсортированный по дате и времени.
3. **Главная страница и выбор типа встречи (гость).** Гость заходит на главную страницу, где описан сервис, и по кнопке «Записаться» переходит на страницу записи — список типов встреч — и выбирает нужный.
4. **Просмотр календаря (гость).** Гость открывает календарь на ближайшие 14 календарных дней, выбирает дату и видит свободные слоты. Слоты считает бэкенд: рабочие часы минус занятые бронирования, с шагом стартов 30 минут.
5. **Бронирование (гость).** Гость выбирает слот, вводит имя и email, подтверждает. Слот занят на всю длительность типа встречи и исчезает из доступных для всех типов. Если слот уже занят (в том числе одновременным запросом) — бэкенд отвечает `409`, гостю предлагается выбрать другое время.

## Страницы и UX

SPA на React Router. Язык UI — русский; ключевые тексты — дословно как в демо-видео Хекслета, где демо молчит, тексты фиксируются в этом разделе.

| URL | Страница | Кто |
| --- | --- | --- |
| `/` | Главная страница | гость |
| `/event-types` | Страница записи (список типов встреч) | гость |
| `/event-types/:id` | Страница слотов (запись на тип встречи) | гость |

### Главная страница (`/`)

Как в демо: пилюля-бейдж «БЫСТРАЯ ЗАПИСЬ НА ЗВОНОК», H1 «Calendar», подзаголовок «Один экран, понятные слоты, быстрая бронь. Выберите время и запишитесь на звонок без лишних шагов.», кнопка «Записаться →» (ведёт на `/event-types`), карточка «Что доступно прямо сейчас». Буллеты карточки приведены к доменным правилам README (у демо приоритет по текстам, у README — по параметрам):

- «Слоты с 10:00 до 18:00 по будням, шаг 30 минут.»
- «Проверка конфликта при бронировании.»
- «Просмотр предстоящих событий в отдельном разделе.»

H1 «Запись на звонок». Список типов встреч карточками: название, описание, длительность («N мин»), кнопка «Выбрать» → `/event-types/:id`.

### Страница слотов (`/event-types/:id`)

Одна страница с внутренними шагами (URL не меняется), H1 «Запись на звонок»:

1. **Выбор слота** — три колонки, как в демо:
   - «Информация»: блоки «Тип встречи» (название выбранного типа), «Выбранная дата» («Дата не выбрана» | «суббота, 28 марта» — строчными, с днём недели), «Выбранное время» («Время не выбрано» | «10:30 - 11:00»), «Свободно» (число свободных слотов выбранного дня), «Длительности в дне» *(sic, как в демо)* («Нет слотов на этот день» | «N мин»).
   - «Календарь»: сетка Пн–Вс (неделя с понедельника), заголовок «март 2026 г.», кнопки «←» «→»; доступные даты — со счётчиком «N св.», недоступные приглушены; выбранная дата — с оранжевой рамкой.
   - «Статус слотов»: плейсхолдер «Выберите дату в календаре.», далее список строк «HH:mm - HH:mm» со статусами «Свободно»/«Занято»; клик по свободному слоту выделяет его оранжевой заливкой.
   - Кнопки «Назад» (возврат на `/event-types`) и «Продолжить» (disabled, пока не выбран слот).
2. **Подтверждение записи**: карточка «Подтверждение записи» с кнопкой «Изменить» (возврат к шагу 1), полями «Имя» и «Email», кнопкой «Подтвердить запись» на всю ширину.
3. **Успех**: карточка «Бронь подтверждена. До встречи!», кнопка «Забронировать еще» — возврат к шагу 1 с уже пересчитанными слотами и счётчиками.

### Предстоящие события (`/owner/bookings`)

H1 «Предстоящие события». Карточки бронирований: имя гостя жирным, email серым, строка «Слот: YYYY-MM-DD-HH:MM», строка «Создано: DD.MM.YYYY, HH:MM». Сортировка — по дате и времени встречи, ближайшие выше. На странице — переход «Типы встреч» (→ `/owner/event-types`) для навигации по зоне владельца.

### Типы встреч (`/owner/event-types`)

H1 «Типы встреч». Список типов карточками: название, описание, длительность. Кнопка «Новый тип встречи» → `/owner/event-types/new`. На странице — переход «Предстоящие события» (→ `/owner/bookings`) для навигации по зоне владельца.

### Новый тип встречи (`/owner/event-types/new`)

Форма: поле «Название» (обязательное, до 100 символов), поле «Описание» (необязательное, до 500 символов), поле «Длительность» (выбор из 30/60/90/120 минут), кнопка «Создать тип». После успешного создания — редирект на `/owner/event-types`, чтобы владелец видел созданный тип в списке.

### Состояния и флоу

**Loading:** простые текстовые индикаторы — «Загрузка…» в карточке/списке при запросах (типы, слоты, предстоящие); при отправке формы кнопка disabled с текстом «Отправка…».

**Пустые состояния (empty):**

- Страница записи без типов: «Пока нет доступных типов встреч. Загляните позже.»
- Предстоящие события без броней: «Предстоящих событий нет.»
- Типы встреч владельца: «Типов встреч пока нет.» + кнопка «Создать первый тип» (→ `/owner/event-types/new`).

**Ошибки (error):**

- 404 типа встречи на `/event-types/:id`: «Тип встречи не найден.» + ссылка «К списку типов» (→ `/event-types`).
- Сбой сети/5xx при загрузке данных (типы, слоты, предстоящие): «Не удалось загрузить данные. Проверьте соединение и попробуйте снова.» + кнопка «Повторить».
- Сбой при создании брони (не 409: сеть, 5xx, 400): на шаге подтверждения показывается текст ошибки от сервера (или общий «Не удалось создать бронь. Попробуйте ещё раз.»), кнопка снова доступна.
- Сбой при создании типа: текст ошибки от сервера рядом с формой, кнопка снова доступна.
- Дата вне окна бронирования и выходные — не error-состояние: календарь не даёт их выбрать (даты приглушены).

**Флоу 409 при бронировании:** после нажатия «Подтвердить запись» и ответа 409 гость возвращается к шагу выбора слота, слоты перезапрашиваются (`GET …/slots`), выбранный слот сбрасывается, над списком показывается сообщение «Это время уже занято. Выберите другое время.».

**Сетка слотов дня:** карточка «Статус слотов» строит полную сетку дня из рабочих часов и шага 30 минут (последний старт — конец встречи не позже 18:00); слоты, отсутствующие в ответе API, показываются как «Занято» (приглушённая строка). При полностью занятом дне — все строки «Занято», счётчик «Свободно 0».

**Экран успеха** — демо-состав без добавлений: «Бронь подтверждена. До встречи!» + «Забронировать еще»; выбранные дата и время остаются видны в колонке «Информация».

## API

Контракт описан в `contract/main.tsp`, машиночитаемая спецификация — `contract/openapi.yaml`. Таблица ниже — краткий обзор; при расхождении источник правды — `openapi.yaml`.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка работоспособности |
| `GET` | `/api/event-types` | Список типов встреч |
| `POST` | `/api/event-types` | Создать тип встречи (владелец) |
| `GET` | `/api/event-types/:id/slots?date=YYYY-MM-DD` | Свободные слоты типа на дату (внутри окна 14 дней) |
| `GET` | `/api/bookings` | Предстоящие бронирования всех типов (владелец) |
| `POST` | `/api/bookings` | Создать бронирование (гость) |

Коды ошибок: `400` — невалидные данные (невалидные форматы `date`/`startTime`, дата вне окна); при бронировании — также слот, не предусмотренный расписанием (выходной день, время вне 10:00–18:00, старт не на сетке 30 минут, встреча не укладывается до 18:00); `404` — тип встречи не найден (неизвестный `eventTypeId` — и в слотах, и в бронировании); `409` — **только** когда слот валиден по расписанию, но пересекается с существующей бронью. Формат ошибки: `{ "error": "описание" }`, тексты дословные:

| Код | Ситуация | Текст |
| --- | --- | --- |
| 400 | Невалидный формат или несуществующая дата | `Некорректная дата: ожидается формат YYYY-MM-DD.` |
| 400 | Дата вне окна бронирования | `Дата вне окна бронирования: запись открыта на 14 дней, начиная с завтрашнего дня.` |
| 400 | Невалидный формат `startTime` | `Некорректное время начала: ожидается формат HH:mm.` |
| 400 | Слот не предусмотрен расписанием (выходной, вне 10:00–18:00, не сетка 30 мин, конец позже 18:00) | `Выбранное время недоступно для записи.` |
| 400 | Нет query-параметра `date` в запросе слотов | `Параметр date обязателен.` |
| 400 | Пустое название типа после тримминга | `Название обязательно.` |
| 400 | Название длиннее 100 символов | `Название не должно превышать 100 символов.` |
| 400 | Описание длиннее 500 символов | `Описание не должно превышать 500 символов.` |
| 400 | Длительность не из набора 30/60/90/120 | `Длительность должна быть 30, 60, 90 или 120 минут.` |
| 400 | Пустое имя гостя после тримминга | `Имя обязательно.` |
| 400 | Имя длиннее 100 символов | `Имя не должно превышать 100 символов.` |
| 400 | Email не проходит шаблон или длиннее 254 символов | `Некорректный email.` |
| 404 | Неизвестный `eventTypeId` (слоты и бронирование) | `Тип встречи не найден.` |
| 409 | Слот пересекается с существующей бронью | `Это время уже занято. Выберите другое время.` |

`GET /api/bookings` — «предстоящие» по дате: все брони с сегодняшней даты включительно (Asia/Almaty), уже начавшиеся сегодня входят в список; сортировка по дате и времени встречи, ближайшие выше. Запрос слотов на выходной день — пустой список, не ошибка.

## Модели данных

```js
// Тип встречи
EventType = { id, title, description, durationMinutes }

// Бронирование
Booking = { id, eventTypeId, date, startTime, endTime, guestName, guestEmail }
```

`id` — строки (UUID). Даты — строки `YYYY-MM-DD`, время — `HH:mm`, всё в часовом поясе `Asia/Almaty`. `endTime = startTime + durationMinutes` соответствующего типа встречи.

### Правила валидации входных данных

- Все строковые поля ввода триммятся на бэкенде **до валидации и хранения**; ограничения длины применяются после тримминга (строка из одних пробелов не проходит `@minLength(1)`).
- `title` типа встречи: 1–100 символов. Дубликаты названий разрешены — типы различаются по `id`.
- `description` типа встречи: необязательное, допустима пустая строка; до 500 символов.
- `durationMinutes`: одно из значений **30, 60, 90, 120** (кратно 30 — концы встреч остаются на получасовой сетке стартов).
- `guestName`: 1–100 символов после тримминга.
- `guestEmail`: простой шаблон `^[^\s@]+@[^\s@]+\.[^\s@]+$` (после тримминга) — ловит опечатки, не претендует на полный RFC; до 254 символов.

Границы зафиксированы в контракте (`contract/main.tsp` — `@minLength`/`@maxLength`/`@minValue`/`@maxValue`/`@format`); кратность длительности и тримминг декларативно не выражаются и проверяются сервером.

## Приёмочная матрица тестов

Критерий «реализация завершена» — вся матрица ниже покрыта зелёными тестами, плюс зелёный `mise run check` и успешная сборка Docker-образа. Бэкенд: Jest + Supertest; фронтенд: Vitest + Testing Library с **замоканным SDK** (реальный бэкенд из фронтенд-тестов не поднимаем). Вёрстка, стили и кроссбраузерность тестами не покрываются — ручная проверка + сборка Docker-образа.

### API (Jest + Supertest)

**Слоты — `GET /api/event-types/:id/slots`:**

- свободный будний день, тип 30 мин: 16 слотов, старты 10:00–17:30 с шагом 30 мин, конец последнего — 18:00;
- тип 120 мин на свободный день: последний старт 16:00 (конец ровно 18:00);
- выходной (сб/вс) → `200` и пустой список (не ошибка);
- сегодня, вчера и `завтра+14` → `400` «Дата вне окна бронирования…»; `завтра` и `завтра+13` → `200`;
- битый формат `date` → `400`; отсутствующий `date` → `400` «Параметр date обязателен.»;
- неизвестный `id` → `404` «Тип встречи не найден.»;
- занятый интервал исключает пересекающиеся старты, **в том числе брони других типов**; back-to-back (старт ровно в момент конца брони) доступен.

**Бронирование — `POST /api/bookings`:**

- успех: `201`, в ответе `endTime = startTime + durationMinutes` типа;
- `409` при пересечении с существующей бронью (включая бронь другого типа); back-to-back — не `409`;
- конкурентность: два одновременных запроса на один слот → один `201`, другой `409` (атомарный check-and-set);
- `400`: дата вне окна, выходной, старт не на сетке 30 мин, вне рабочих часов, конец позже 18:00, невалидные форматы `date`/`startTime`;
- `400`: пустое имя после тримминга, имя длиннее 100, email без шаблона, email длиннее 254;
- неизвестный `eventTypeId` → `404`;
- тексты ошибок — дословно по таблице из раздела «API».

**Типы встреч — `POST`/`GET /api/event-types`:**

- создание: `201`; дубликаты названий разрешены (два типа с одним `title` → оба `201`);
- `400`: пустой `title`, `title` > 100, `description` > 500, `durationMinutes` не из 30/60/90/120;
- тримминг: строки с пробелами по краям хранятся обрезанными;
- список возвращает созданные типы.

**Предстоящие — `GET /api/bookings`:** брони с сегодняшней даты включительно (уже начавшиеся входят), вчерашние исключены; сортировка по дате и времени, ближайшие выше; пусто → `200` `[]`.

**Health — `GET /api/health`:** `200` `{ "status": "ok" }`.

### Фронтенд (Vitest + Testing Library, SDK замокан)

- **Главная:** ключевые тексты, переход по «Записаться →»;
- **Страница записи:** список типов из мока; empty-текст; error + кнопка «Повторить»;
- **Страница слотов:** выбор даты → запрос слотов; выбор слота активирует «Продолжить»; 404 типа → «Тип встречи не найден.»;
- **Флоу брони:** слот → форма → успех («Бронь подтверждена. До встречи!») → «Забронировать еще»;
- **409-флоу:** мок 409 → возврат к слотам, перезапрос, сообщение «Это время уже занято. Выберите другое время.»;
- **Предстоящие события:** рендер карточек; empty «Предстоящих событий нет.»;
- **Создание типа:** сабмит → POST → редирект на `/owner/event-types`; ошибка → текст у формы.

Валидация форм на клиенте — нативные HTML5-атрибуты (`required`, `type="email"`, `maxLength`); кастомных сообщений нет, тексты ошибок приходят от сервера.

## Правила для ИИ-агентов

1. **Хранилище только в памяти** — см. раздел «Хранение данных». Никаких БД и файловых сохранений.
2. **Contract-first:** любое изменение API начинается с правки `contract/main.tsp`, затем `npm run compile` → реализация на бэкенде → `npm run generate:api`. Сгенерированные файлы (`openapi.yaml`, `client/src/api/generated/`) руками не править.
3. Фронтенд ходит в API **только через сгенерированный SDK**.
4. Доменные правила (окно 14 дней, рабочие часы, шаг 30 минут, запрет пересечений, атомарность бронирования) — инварианты. Их изменение — только по явному запросу, с обновлением этого README и тестов.
5. **Сначала бэкенд, потом фронтенд:** новая возможность = сначала эндпоинт + тест на него, затем UI. Новые ресурсы API — новый файл в `server/src/routes/`.
6. После изменений запускать `mise run check` из корня (или `npm test` и `npm run lint` в затронутом пакете); задача считается выполненной только при зелёных проверках. Перед сдачей проверить, что проект собирается в Docker-образ.
7. Минимальные изменения: не рефакторить и не переименовывать существующий код без запроса.
8. Не удалять и не переименовывать `.github/workflows/hexlet-check.yml` и сам репозиторий.
